## The workflow (both directions are valid)

Jobs can originate on either side. The **PO Number is the shared identifier**
that lets the two systems merge on any given job.

**Path A — Job starts in the CRM:**
1. Nick or Wesley creates a Project in the CRM. CRM generates a PO.
2. When ready to send it out to bid, admin opens the Bid Portal and creates
   a Job, typing the CRM's PO into the PO field.
3. Portal and CRM are now linked on that PO.

**Path B — Job starts in the Bid Portal (common during the CRM build-out):**
1. Admin opens the Bid Portal and creates a Job. The PO field is left blank.
2. Portal auto-generates a PO (like `PO-2026-0001`) and assigns it to the job.
3. Later, when the job is officially entered into the CRM, the CRM adopts
   that same PO from the portal and links the two records.

Either way, **one PO = one job across both systems.** The merge always happens
on PO, so there are no duplicates.

---

## PO generation and format

- **Format:** `PO-YYYY-NNNN` (example: `PO-2026-0001`)
- The portal generates the next number in sequence based on existing jobs
  created this year, avoiding collisions with any manually entered POs.
- Every job payload carries a `poAutoGenerated` flag so the CRM knows whether
  the PO came from the portal (adopt it) or the CRM (already exists).
- Because both sides could theoretically generate the same PO number, once
  integration is live, the CRM should own the sequence — the portal defers to
  the CRM's next-PO endpoint if online, otherwise generates locally and syncs.

---

## Merge logic (CRM side)

When the CRM receives a payload from the portal, or when a user creates a
project in the CRM that references a PO:

1. **PO Number match** — if `payload.job.poNumber` matches an existing CRM
   project's PO → attach/merge. Never duplicate.
2. **No match, `poAutoGenerated: true`** → adopt this PO as-is. Create the
   CRM project with this PO number so the two sides are permanently linked.
3. **No match, `poAutoGenerated: false`** → user typed a PO that doesn't
   exist in either system. Prompt: *"PO `XXX` not found in the CRM. Create
   new project?"*
4. **Project ID match (secondary)** — if `payload.job.projectId` matches a
   CRM project that has a DIFFERENT PO than the payload → prompt the user
   about the conflict. Never silently overwrite.

## What data flows between systems

### Bid Portal → CRM (job created / updated)

Whenever a job is added or edited on the portal:
- Job title, address, bid due date
- **PO Number** (primary merge key)
- **CRM Project ID** (optional secondary reference)
- `poAutoGenerated` flag
- Project Manager (id, name, email, phone)
- Estimator (id, name, email, phone)
- Scope + Specifications (text + attached documents)
- Visibility (public/private)
- Attached plans (metadata + storage URLs)

### Bid Portal → CRM (during bidding)

- Bid submitted (bidder company, contact, amount, scope, notes, timestamp)
- Bid accepted / rejected
- Sub activity (viewed job, downloaded plan X at time Y)
- Job status changes (open → closed → won → lost)

### Bid Portal → CRM (estimate handoff)

When an admin finalizes an estimate:
- Estimate number, status
- Line items (with source flag and `bidId` back-reference)
- Direct cost, margin %, margin dollars, grand total
- Notes
- Accepted bids that contributed

The "Copy CRM Payload" button produces exactly this payload today.

### CRM → Bid Portal (future)

- When a CRM project's PO changes, sync to the linked portal job
- "Send to Bid Portal" button on CRM Project view creates a portal job
  pre-filled with PO, Project ID, title, address, scope

## Where the data lives on the CRM side

Each CRM Project has these tabs:

- **Overview** — client, address, PO, contract value (existing)
- **Bid Portal** (new) — read-only view of the linked portal job with bids,
  activity, plans
- **Documents** — scope docs, spec docs, plans imported from the portal
- **Estimator** (existing) — receives the portal's estimate payload as the
  starting point; can be refined on the CRM side without touching the portal
- **Bids** — flat list of all bids received on the linked portal job
- **Activity** — merged timeline: portal events + CRM events

## Data safety / duplicate prevention

- CRM import endpoint MUST be idempotent — re-sending same payload updates,
  doesn't duplicate. Dedupe by `estimate.id`.
- Portal job's PO changes → CRM unlinks from old project, links to new. Log
  the change event.
- Portal job deleted → CRM keeps import records but soft-deletes the link.
- Portal-generated PO numbers should be respected as-is by the CRM to keep
  the shared identifier stable.

## Sub sync — locked 2026-09-08

**Model:** the portal is the primary place subs create and maintain their own
company info (contact, address, licenses, insurance, W-9, trades). The CRM
mirrors this data as a Contact/Vendor record so estimators, PMs, and A/P
staff can see the same info from inside the CRM without going back to the portal.

**Sync direction:** BIDIRECTIONAL. Portal updates flow to CRM automatically;
CRM edits flow back to portal. Last write wins on individual field level
(not whole record). See conflict handling below.

**Trigger:** on sub signup, on any sub profile edit, on any doc upload/update.

### CRM-side duplicate detection

The portal has already run its own duplicate check at signup and shown warnings
to the sub if a possible match existed in the portal. But the CRM may have
subs that predate the portal (imported from spreadsheets, old ERP, etc.),
so the CRM must ALSO run duplicate detection when it receives this payload:

**Auto-merge (safe):** if the CRM finds a contact where BOTH
`company.legalName` matches (case-insensitive, punctuation-normalized) AND
`company.address` matches (case-insensitive, first line only), auto-merge:
- Fill in any CRM fields that were blank
- Do NOT overwrite CRM fields that have values (portal is filling gaps, not
  clobbering CRM data on first link)
- Set `crm.contact.portalUserId = payload.portalUserId`
- Send an alert to Wesley/Nick: "Auto-linked portal signup Jane Doe / ABC
  Drywall to existing CRM contact. Review here."

**Prompt for review:** if company name matches but address doesn't (or vice
versa), OR email matches but nothing else, create a REVIEW QUEUE entry.
Admin sees a side-by-side comparison and clicks "Same company → merge" or
"Different company → create new".

**No match:** create a new CRM contact/vendor record with all payload data
and set `crm.contact.portalUserId = payload.portalUserId`.

### Field-level conflict resolution (bidirectional sync)

Once portalUserId is linked on the CRM side, both systems can edit the
sub's info. To prevent overwriting valid changes:

1. Every field carries a `lastEditedAt` timestamp and `lastEditedBy` marker
   (either `"portal:{userId}"` for sub self-edits or `"crm:{adminId}"` for
   admin edits in CRM).
2. When a sync payload arrives, compare per-field timestamps. Only update
   fields where the incoming timestamp is newer than the destination's.
3. Documents are treated as replacements, not merges — newest upload wins.
   Old versions kept in Supabase Storage for audit trail (90-day retention).

**Example conflict:** admin edits `phone` in CRM at 10:00am. Sub edits
`phone` in portal at 10:05am. Portal syncs to CRM at 10:05am. CRM sees
`portalPhone.lastEditedAt (10:05) > crmPhone.lastEditedAt (10:00)`, accepts
the portal value. Sub's edit wins, correctly.

### What flows CRM → Portal

The CRM should push these events back to the portal via
`/api/portal/sub-updated`:

- Admin edited sub's contact info in CRM
- Admin added a note that should be visible to sub
- Admin marked sub as inactive / do-not-invite
- Admin uploaded a doc on sub's behalf (e.g., signed MSA)

Portal receives these and updates its local record. The sub sees the
change on their next login.

### Documents flow

W-9 and insurance certificates uploaded in either system are stored in
Supabase Storage (bucket: `sub-docs`, path: `{portalUserId}/{filename}`).
Both portal and CRM read from the same bucket — no file duplication.

**Expiration tracking:** the portal checks doc `expiresAt` on every load
and flags documents expiring within 30 days. If a doc expires without
replacement, the sub is BLOCKED from submitting new bids (existing bids
remain valid). CRM should show the same expiration status.

**Storage path convention:** `sub-docs/{portalUserId}/{docType}-{YYYY}.pdf`
- `sub-docs/u_1725840000000/w9-2026.pdf`
- `sub-docs/u_1725840000000/coi-gl-2026.pdf`
- `sub-docs/u_1725840000000/license-tn-gc.pdf`

### API endpoints (CRM-side, to be built)

- `POST /api/portal/sub-sync` — accepts sub payload above
- `GET /api/portal/sub/{portalUserId}` — CRM's current state of this sub (for portal to compare)
- `POST /api/portal/sub/{portalUserId}/review-queue-decision` — admin resolves a manual-review-queue item
- `POST /api/portal/sub-updated` — CRM pushes updates back to portal

### Security

- All sub sync endpoints require CRM-side service token (never a portal user token)
- Sub payloads never include another sub's data
- CRM never sends its own admin-only data (internal notes, credit ratings, past disputes) to the portal
